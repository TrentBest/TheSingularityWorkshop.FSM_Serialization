# Architecture Diagrams

Capture system/package boundaries, components, dependency direction, build/runtime relationships, deployment context, and external interfaces where they matter. Keep the repository's real dependency graph separate from conceptual future architecture.

Every edge should have a stated meaning and evidence/provenance. Label planned or conceptual relationships rather than drawing them as implemented facts. Link to source projects, package metadata, tests, and relevant use cases.

Generated architecture views should consume the shared normalized model; broader manually authored context remains explicitly marked as such.
